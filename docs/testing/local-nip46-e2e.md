# ローカル NIP-46 E2E 動作確認

Nostr Live Canvas をブラウザで操作し、`nak bunker` による NIP-46 接続・署名と、`nak serve` への投稿・再取得を確認する。実アカウントや公開リレーは使用しない。

## 確認する範囲

```text
ブラウザ上の Nostr Live Canvas
  ├─ NIP-46要求 → localhost の nak serve → nak bunker
  └─ 署名済み投稿 → 同じ nak serve → アプリ / 独立した検証用購読
```

- リモート署名器のURL入力によるログイン。
- ローカルのプロフィール・フォローリスト・投稿の表示。
- ブラウザの Publish 操作 → `sign_event` → リレー受信 → 署名検証。
- 再読込後のセッション復元と、リレーからの投稿再取得。
- 終了時の鍵・ペアリング情報・プロセスの片付け。

ブラウザ操作は手動、またはブラウザを操作できる開発支援ツールで行う。補助スクリプトは環境準備と受信検証を担当するもので、ブラウザの自動テストスイートではない。

リポジトリの Rust リレー、DynamoDB、公開リレー、実拡張の NIP-07、スマートフォンの QR 読取り、Blossom 画像アップロードはこの手順の検証対象外。

## 前提と安全上の約束

- アプリの起動コマンドとブラウザを、同じマシンで動かす。クラウド環境の `localhost` は Mac のブラウザからは見えない。
- Node.js 22 以降、npm、Git、`nak`、Chrome などのブラウザを用意する。
- `nak serve --help` と `nak bunker --help` が動くことを確認する。`nak --version` が `debug` でも、Go のビルド情報で版を確認できる。
- `http://127.0.0.1:3321` はこのテスト専用の origin として使う。別のアプリや実アカウントに使っている場合は実行せず、全接続先と削除先のポートを一括で見直す。
- ログイン済みの実アカウントや既存秘密鍵は使わない。画面では必ず「リモート署名器でログイン」を選ぶ。
- `nak bunker --persist`、`--profile` は使用しない。秘密鍵をファイルやコマンドライン引数に保存しない。
- `bunker://...`、`nostrconnect://...` はペアリング用の秘密情報を含む。ログ、スクリーンショット、チャット、PR に載せない。
- この手順では、毎回新しいテスト鍵をプロセス内で生成する。停止すると鍵とリレー内のイベントは失われる。
- `.env*` はテスト用コピーに含めない。追加の認証情報が必要な変更を検証する場合は、この手順の範囲を見直す。

未導入の場合は [nak 公式リポジトリ](https://github.com/fiatjaf/nak) の手順で用意する。動作確認時は既存の v0.17.1 を使用しており、インストールやシステム設定変更は行っていない。

## 1. 対象の作業ツリーを確認する

確認したいソースがあるリポジトリのルートで実行する。

```bash
pwd
git status --short
git rev-parse HEAD
node --version
npm --version
command -v nak
nak --version
nak serve --help
nak bunker --help
# Go がある場合。nak が debug と表示されるときにも使える。
go version -m "$(command -v nak)"
```

補助例は、渡したリポジトリの `apps/web` を一時ディレクトリにコピーする。**コミット済みの HEAD だけでなく、作業中の変更・未追跡ファイルも対象**になる。元の作業ツリーには書き込まない。

コピー対象から `node_modules`、`.next`、`.git`、`.vercel`、`coverage`、`.env*` を除外する。シンボリックリンクがある場合は停止する。秘密情報を別名のファイルに置いている場合は、実行前にコピー対象を確認する。

アプリに関係しない staged changes をリセット・stash する必要はない。別の作業ツリーから補助例を使う場合は、スクリプトのパスと最後の引数をそれぞれ明示する。

## 2. 隔離したローカル環境を起動する

```bash
node docs/testing/examples/local-nip46-e2e.cjs "$PWD"
```

[補助例のソース](examples/local-nip46-e2e.cjs) を使用する。起動したターミナルは終了まで開いたままにする。

表示例。ディレクトリ名は実行ごとに変わる。

```text
Temporary test directory: /.../nostr-nip46-e2e-XXXXXX
Ready: http://127.0.0.1:3322
App: http://127.0.0.1:3321
Post exactly: Local NIP-46 E2E test: signed by nak, localhost only.
Result: /.../nostr-nip46-e2e-XXXXXX/result.json
```

起動時に行われること：

1. `3321`、`3322`、`10549` が空いているか確認。使用中なら既存プロセスを止めずに終了。
2. アプリを OS の一時ディレクトリにコピーし、そのコピー内で `npm ci --ignore-scripts --no-audit --no-fund` を実行。
3. コピー内だけに次のテスト設定を適用。
   - `BOOTSTRAP_RELAYS` を `ws://127.0.0.1:10549` に固定。
   - `window.nostr.js` の `wnjParams.nostrConnectRelays` も同じリレーに固定。
   - `appMetadata.image` をローカルの `/icon.svg` に固定。
   - CSP の `connect-src` で localhost のアプリとリレー以外を禁止。
4. 使い捨ての秘密鍵から初期イベントを作り、標準入力経由で `nak serve --hostname 127.0.0.1 --port 10549` に渡す。
5. その鍵を子プロセスの `NOSTR_SECRET_KEY` として `nak bunker ws://127.0.0.1:10549` を起動。秘密鍵と nak の生ログは保存しない。
6. Next.js と、ペアリングURLを受け渡すローカル補助ページ、独立した受信検証用購読を起動。

`npm ci` と Next.js のフォント取得などには外部ネットワークを使う場合がある。「localhost のみ」は **Nostr の署名・イベント通信先**を指し、マシン全体のオフライン動作ではない。

### 初期イベント

| kind | 内容 | 必要な理由 |
| --- | --- | --- |
| 0 | `Local E2E Test` のプロフィール | 表示名を確認する |
| 3 | テスト鍵自身をフォローする `p` タグ | 初期feedにfixtureと自分の投稿を表示する（空フォローの検証は後述） |
| 10002 | ローカルリレーだけの `r` タグ | リレー設定を明示する |
| 1 | `Local relay fixture: browser E2E ready` | 初期受信の基準にする |

アプリは kind:10002 に指定されたリレーだけでなく `BOOTSTRAP_RELAYS` も使う。このため、kind:10002 をローカルにするだけでは公開リレーを避けられない。上記3か所の通信設定と CSP をまとめて使う。

## 3. ブラウザでペアリングする

1. `http://127.0.0.1:3322` を開く。
2. 初回も「Clear test credentials」を開き、「Clear local test credentials」を押す。前回異常終了時のテスト情報が残っていても、今回の接続に混ざらないようにする。
3. 補助ページに戻り、「Copy local test signer URL」を押す。
4. `http://127.0.0.1:3321` を開く。
5. 「リモート署名器でログイン」を押す。
6. 署名器の入力欄にコピーした `bunker://...` を貼り付け、「Connect »」を押す。
7. キャンバスに「接続済み」と、初期投稿 `Local relay fixture: browser E2E ready` が表示されることを確認する。

署名器は `nak bunker` の既定の一度限りのペアリング secret によって、接続してきたテストクライアントを認可する。秘密鍵そのものをアプリへ渡す操作はない。

**ブラウザ操作ツールのクリップボードについて：** ページの Copy ボタンとツールの仮想クリップボードが別の場合がある。その場合は補助ページの `/pairing-value` をブラウザで開き、画面上の値を入力欄へ受け渡す。値は出力・保存せず、観測結果を表示する場合も URL 全体を伏せる。シェルでシステムのクリップボードやブラウザ内部ストレージを直接操作する方法には切り替えない。

## 4. 投稿、署名、受信を確認する

1. キャンバス上部の「投稿」を押す。
2. 次のテスト文を入力する。

   ```text
   Local NIP-46 E2E test: signed by nak, localhost only.
   ```

3. `Publish` を押し、その本文のカードが表示されることを確認する。
4. `http://127.0.0.1:3322/status` または起動時に表示された `result.json` を確認する。
   - `signerMethods` に `connect`、`get_public_key`、`sign_event` がある。
   - `receivedNotes` に上記の本文がある。
   - その `pubkey` がテストの `pubkey` と一致する。
   - `signatureValid` が `true`。
   - `errors` が空。
5. アプリのページを再読込し、接続とカードが復元されることを確認する。

`Publish` 直後のカード表示だけでは合格にしない。アプリには楽観的表示があるため、独立した購読での受信と署名検証、再読込後の再取得まで確認する。

CLI で非秘密情報の結果を確認する例：

```bash
curl -fsS http://127.0.0.1:3322/status
```

必要なら `result.json` の `relayPid`、`signerPid` を使い、macOS で通信先を確認する。プロセスの全環境変数を表示しない。

```bash
lsof -nP -a -p "<relayPid>,<signerPid>" -iTCP
```

`127.0.0.1:10549` の待受とループバック接続だけであること、アプリレスポンスの CSP が想定どおりであることを確認する。

```bash
curl -fsSI http://127.0.0.1:3321/ | grep -i content-security-policy
```

## 5. 任意の購読・配置シナリオ

基本の投稿・再取得を確認した後、補助ページの次のボタンで追加検証できる。どちらも使い捨て鍵で事前署名したイベントだけをlocalhostへ送る。1回のrunner起動につき各1回だけ利用可能。

- **Schedule eight stream fixtures**: 5秒後から800ms間隔で、本文の長さが異なる8件のノートを送る。アプリへ戻り、既存カードをholdした状態や下書き入力中に、新着カードが届いても画面が停止せず操作できることを確認する。解除とウィンドウ幅変更も確認する。
- **Replace with empty follows**: 新しいkind:3（pタグなし）を送る。アプリを再読込し、接続済みの空feedになり、接続中のまま停止しないことを確認する。自己フォローは自動追加しないため、既存fixtureが消えるのは正常。

送信済みイベントのIDとkindは `/status` の `scenarioSent` に記録する。これらの送信操作は補助ページの同一originのPOSTだけ受け付ける。空フォローへ切り替えた後に基本の再取得確認を行いたい場合は、片付け後にrunnerを新しく起動する。

この目視確認だけでholdの全配置や非同期競合を網羅したとは扱わない。循環・重なり・リポスト取得待ちの競合は[購読・配置契約](../architecture/live-canvas-contracts.md)の回帰テストで確認する。

## 6. 片付ける

順序を守る。先にサーバーを停止すると、ブラウザ用の削除ページが開けなくなる。

1. `http://127.0.0.1:3321/e2e-cleanup.html` を開く。
2. 「Clear local test credentials」を押す。
3. `Local test credentials and pairing clipboard cleared.` と表示されることを確認する。このテスト origin 内の `wnj:*`、`nostr-relay:*` を削除し、クリップボードを空にする。別の内容をコピーしていた場合は、必要に応じて先に保存する。
4. テスト用タブを閉じる。
5. 起動ターミナルで Ctrl+C。runner が自身の子プロセスを停止し、鍵とペアリングURLを破棄する。
6. 待受が消えたことを確認する。

   ```bash
   lsof -nP -iTCP:3321 -iTCP:3322 -iTCP:10549 -sTCP:LISTEN
   ```

出力が残る場合は PID を `result.json` と照合する。`killall node`、`pkill nak` などで他の作業を巻き込まない。`result.json` の `stopped: true` は停止処理を実行した印であり、待受確認の代わりにはならない。

一時ディレクトリにはアプリのコピー、依存パッケージ、非秘密情報の `result.json`、インストール・アプリのログが残る。確認後、表示された一時ディレクトリだけを削除してよい。実行結果を保存するなら commit SHA、ブラウザ、nak/Node の版、確認項目、イベントID、署名検証結果を残す。秘密鍵、ペアリングURL、ブラウザの localStorage、生の bunker ログは残さない。

異常終了してブラウザの情報だけ残った場合は、次回起動後に手順3の削除ページから先に片付ける。元リポジトリの `git status` も実行前と比較する。

## 問題が出たとき

- **`localhost` に接続できない：** サーバーとブラウザのマシン、IP、ポートを確認する。サンドボックス間で localhost が分離されることがある。ネットワーク制限やセキュリティ警告を解除して回避しない。
- **`nak` が `debug` と表示される：** `go version -m "$(command -v nak)"` の module version を記録する。
- **`nak bunker connect` を使いたい：** 確認した nak v0.17.1 では逆向きの client-initiated flow は未実装。この手順は `nak bunker` が出す URL をアプリに入力する方向を使う。
- **QR が大きすぎる：** ブラウザ操作環境が favicon を data URL に置換すると、QR に含めるメタデータが大きくなることがある。補助例は `appMetadata.image` をローカル画像に固定する。QR 読取りの成功自体は本手順の合格条件ではない。
- **feed が空：** kind:3 の `p` タグと、その鍵に対応する初期イベントを確認する。フォローが空なら接続済みの空feedになる。fixtureを期待する場合は自己フォローがある基本シナリオで確認する。
- **ログインできない：** 前回のブラウザ情報を削除し、今回の補助ページから新しい URL をコピーする。既存の実アカウントへ切り替えない。
- **設定パッチが一致せず停止：** アプリ側の構造や next.config が変わっている。補助例はその場合に停止する。対象箇所と通信先を見直してから更新し、公開リレーへのフォールバックは作らない。
- **依存インストールが失敗：** `install.log`、Node の版、npm/JSR への通信を確認する。lockfile を書き換えて通すのではなく、環境・依存の問題として切り分ける。

## 確認記録と次の用途

2026-11-09、lakche.local（macOS ARM64、Node.js v22.16.0、npm 10.9.2、nak v0.17.1）で、main `c4b8c365db8a0c071cd45d46c85ece59f7419c59`、Next.js 16.4.3、window.nostr.js 0.8.1 を使って本手順の接続・署名・受信・署名検証・再読込を実証した。上記補助例は、そのときの一時スクリプトを再利用しやすい形に整理したもの。

補助例の整理後には、起動コマンド、NIP-11 応答、localhost 限定 CSP、CLI クライアントからの2回の署名・受信・署名検証、ペアリングURL更新後の別クライアント接続を確認した。起動前確認の後に補助ページ用ポートを占有する異常系も実行し、失敗時に自身の relay・signer・app が停止して3ポートすべて解放されることを確認した。これらはブラウザ操作の再実施ではなく、補助例自体の接続・後始末を確認する追加チェックである。

今後は、返信、リアクション、ログアウト、署名待機中のキャンセルなどのケースを、この隔離構成に追加できる。自動ブラウザテストや CI に組み込む際は、固定 fixture、成功条件、タイムアウト、異常終了時の後始末を別途テストコードとして整備する。本書の存在だけでそれらを検証済みとは扱わない。
